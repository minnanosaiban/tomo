英文構造アナライザー

集めた英文をＡＩで分解して学ぶ、ＴＯＥＩＣ対策向けの英語学習アプリです。間違いの記録や復習の管理、英文の自動生成も備えています。文の構造（ＳＶＯＣ・文型・時制）の解説、英文と単語のグループ分け、関係図、絵文字イラスト、読み上げ・音声練習を、1つの画面で切り替えて使います。英文は端末に保存し、クラウド同期を使うときは端末の中で暗号化してから送ります。

  • 公開ページ：eng-analyzer.scratch-2026-10-07-cb3f9c.workers.dev
  • ソース：github.com/minnanosaiban/eng-analyzer

このページは、その仕組みと、作るうえで判断したことの解説です。発想は、Qiita の記事「英文構造を一発で分解するアプリ」を参考にしています（撮影・OCR の機能は省き、集めた英文を貼り付ける形にしました）。

全体の構成


ビルド工程のない素の HTML / CSS / JavaScript です。画面は index.html の1ファイルにまとめ、Cloudflare Workers の静的アセットとして配っています。サーバー側のコードは、同期用の API（/api/*）だけです。

public/
  index.html       画面・スタイル・処理のすべて
  sw.js            Service Worker（オフライン用キャッシュ）
  manifest.json    ホーム画面に追加するための設定（PWA）
  relagrid/        関係図の描画部分（RelaGrid から同梱）
  vendor/qrcode.js QRコードの生成（qrcode-generator、同梱）
  samples/         試すための英文（CSV と、解析済みの JSON）。アプリに同梱
src/worker.js      同期 API。暗号文の保存と取得だけ
migrations/        D1（データベース）のテーブル定義（同期・受信箱）
tools/             inbox-send.mjs（受信箱へ英文を預けるスクリプト）
CLAUDE.md          Claude Code が英文を入れる手順
wrangler.jsonc     Workers の設定（静的アセット + D1）

wrangler.jsonc の run_worker_first で、/api/* だけを Worker に回し、それ以外は静的ファイルをそのまま返します。画面を開くだけなら Worker は動かないので、無料枠の回数を消費しません。

5つのモード

モード すること ＡＩ
⑴ 構造化 和訳・スラッシュリーディング・区切りごとの形・品詞の色分け・ＳＶＯＣ・文型・時制・単語（発音記号つき）・ＴＯＥＩＣの観点・4択問題 使う
⑵ 英文グループ化 解析結果（文型・時制・パートなど）で自動分類／ＡＩがグループ案を出す 自動分類は不要
⑶ 関係図化 ＳＶＯＣと修飾関係を RelaGrid で図にする 解析結果から作るなら不要
⑷ イラスト化 英文の場面を絵文字で配置した図にする 使う
⑸ 英単語グループ化 単語帳と、品詞・頻出度・意味などでのグループ分け 自動分類は不要

この5つに加えて、学習を続けるための「弱点集計」と、英文を自分で集める手間を減らす「英文生成」があります。音声（読み上げ・シャドーイング・聞き取り）は、モードではなく、どの画面からでも使える機能です（「音声は『画面』ではなく『機能』にした」の節）。

ＡＩを呼ぶのは、ボタンを押したときだけです。結果は英文ごとに保存して使い回すので、同じ英文を何度開いても、ＡＩの呼び出しは1回で済みます。

ＡＩの答えはJSONに固定する

解析は、Gemini に「この形の JSON だけで答えて」と指示して受け取ります。画面はその JSON を読んで組み立てるだけです。自由な文章で返されると、どこが訳でどこが文型かを、毎回推測することになるためです。

"elements":[{"text":"英語の語句","role":"S|V|O|C|M のいずれか","note":"補足"}],
"toeic":{"scene":"ビジネス場面","part":"出題されやすいパート","points":[...]}

ＴＯＥＩＣの観点（場面・パート・論点）も同じ JSON に入れておくと、⑵ の自動分類がＡＩを呼ばずにできます。解析済みの英文の toeic.scene を集めて数えるだけで、「場面：人事」「場面：会議」といったグループ案になります。

コピペモード

ＡＩの使い方は、2通りから選べます。

  • Gemini API：API キーを入れておけば、ボタン1つで自動で返ってきます
  • コピペモード：プロンプトをコピーして、Gemini アプリなどに自分で貼り、返ってきた答えを貼り戻します

コピペモードは、API の料金を払わずに、契約中の Gemini アプリ（Google AI Pro など）の範囲で使うための仕組みです。内部では、API を呼ぶ関数 gemini() の入口で分岐しているだけなので、解析・問題作成・関係図・イラスト・グループ案のどれからでも同じように使えます。

async function gemini(prompt, temp = 0.2) {
  if (isCopyMode()) return copyPaste(prompt + "\n\n【出力形式】JSON だけを ```json のコードブロック1つで出力してください。");
  // …ここから API の呼び出し
}

チャットの答えには、「もちろんです」のような前置きや、コードブロックの記号が付くことがあります。貼り付けられた文から、コードブロックの中身、なければ最初の { か [ から最後の } か ] までを取り出して読み直します（parseLoose）。読めなかったときは画面を閉じずにエラーを出し、貼り直せるようにしています。一括解析は、10文を1つのプロンプトにまとめて、コピペの回数を減らしています。

文を、形ごとに区切って説明する

⑴ の解析画面には、英文を、文法上のまとまりごとに、前から順に区切り、番号と「形」を付けて説明する欄があります。たとえば、次のように出ます。

⑴ Candidates are advised:主語+動詞
⑵ to bring copies of their certificates:to+不定詞句
⑶ to the interview:前置詞句

画面には、番号つきで下線を引いた英文と、区切りごとの一覧（形のラベルつき）が出ます。「テキストでコピー」を押すと、上の書式のテキストが、そのままコピーされます。

スラッシュリーディングとの違い

スラッシュリーディングは、意味のまとまりで区切り、各区切りに日本語の訳を付けます。読む順に意味を取るためのものです。この欄は、文法上のまとまりで区切り、各区切りに形の名前（主語+動詞、to+不定詞句、前置詞句など）を付けます。「この部分は、文法的に何か」を、一覧で確かめるためのものです。区切る位置は、似ていても、同じとは限りません。

解析結果に入れる

解析のＪＳＯＮに、phrases という項目を足しました。区切った英語（t）と、形（f）の組です。

"phrases": [{"t":"Candidates are advised","f":"主語+動詞"}, {"t":"to bring copies of their certificates","f":"to+不定詞句"}, {"t":"to the interview.","f":"前置詞句"}]

品詞の色分けと同じく、ＡＩの返事は、そのままでは使いません。区切りを半角スペースでつなぐと、原文と完全に一致するときだけ採用します。順序が違う、途中が抜けている、区切りが1つだけ、形が空、のどれかなら、区切りだけを付けず、解析の他の部分は、そのまま残します。

function cleanPhrases(ps, text) {
  if (!Array.isArray(ps) || ps.length < 2 || ps.length > 12) return null;
  // …各区切りの t と f を確かめる(f は40字まで)
  return norm(out.map(x => x.t).join(" ")) === norm(text) ? out : null;
}

どこで区切るかを、プロンプトで決める

ＡＩに「文法上のまとまりで区切って」とだけ頼むと、区切り方が、文ごとにばらつきます。そこで、プロンプトに、区切り方の決まりと、例を入れました。例は、上の Candidates are advised… の文そのものです。

  • 文の核（主語・動詞・必要なら目的語・補語）は、まとめて1つにして、「主語+動詞」「主語+動詞+目的語」のように、形を書く
  • to不定詞句・動名詞句・分詞句・前置詞句・副詞（句）・副詞節・関係詞節・名詞節などは、それぞれ、独立した区切りにする
  • 関係詞節が、主語と動詞のあいだに入るときは、核を分ける（「Employees」主語 / 「who work overtime」関係詞節 / 「are entitled」動詞句 / …）
  • 迷ったら、粗く（区切りを少なく）する

色は、形の名前から決める

形のラベルは、ＡＩが自由に付けるので、種類が決まっていません。そこで、ラベルの文字から、色の系統を決めます（節＝ピンク、不定詞・動名詞・分詞＝紫、前置詞＝緑、文の核＝青、ほか＝灰色）。色だけに頼らないよう、ラベルの文字も必ず出しています。

function phraseClass(f) {
  if (/節/.test(f)) return "c";
  if (/不定詞|動名詞|分詞/.test(f)) return "v";
  if (/前置詞/.test(f)) return "p";
  if (/主語|動詞|目的語|補語/.test(f)) return "s";
  return "o";
}

samples の区切りは、位置の番号だけを答えさせて作る

samples の90文には、区切りも先に入れました。ここでも、ＡＩに文字を書き写させると、ずれやすいので、語を並べた表を渡して、「何番目から何番目まで」と、形のラベルだけを答えさせました。 区切りの英語は、その番号から、こちらで組み立てます。だから、原文と、ずれません。

機械で確かめたのは、次のことです。区切りに、すき間も重なりもなく、全部の語を覆っていること。区切りが2〜8個であること。形が空でなく、24字以内であること。90文とも、一度で通りました。最初に示された例（Candidates are advised…）の文は、示された3つの区切りと形に、完全に一致しました。

そのうえで、結果を目で見て、2つ直しました。

  • ラベルの括弧：「接続詞+節(副詞節(条件))」のように、括弧が二重になっていたので、「接続詞+節(副詞節・条件)」に統一しました
  • 命令文：please contact the travel desk に、「主語+動詞+目的語」が付いていました。命令文には主語がないので、「動詞+目的語(命令文)」に直しました

形の判定は、こうした、文の種類に引きずられた間違いが出やすいところです。検査は、区切りの位置が正しいことを確かめますが、形の名前が正しいことまでは、確かめられません。

後から足す

品詞の色分けと、いっしょに判定させます。1回のＡＩの呼び出しで、words（品詞）と phrases（区切りの形）の両方を返させ、まだ無いものだけを入れます。すでに品詞がある英文に、区切りを足すときに、品詞を上書きしないためです。

function applyExtras(it, r) {
  const w = cleanWords(r?.words, it.text);   if (w && !cleanWords(a.words, it.text))     { a.words = w; got++ }
  const p = cleanPhrases(r?.phrases, it.text); if (p && !cleanPhrases(a.phrases, it.text)) { a.phrases = p; got++ }
  return got;
}

1文ずつは、画面の「区切りの形を付ける」、まとめては、ライブラリの「表示中の品詞・区切りの形を一括で付ける」です。受信箱・復元から、同じ英文が届いたときも、区切りが無い英文には、区切りだけを足します（「すでにある英文には、足りないものだけを足す」の節）。

限界

  • 区切りは、前から順の1列です。文の入れ子の構造（たとえば、「to the interview」が、本来は、「bring」にかかる前置詞句であること）は、表せません。入れ子の関係は、「文構造」と、関係図で見ます
  • 形のラベルは、ＡＩの判定なので、誤りが混じります。「命令文に主語を付ける」のような間違いは、samples では直しましたが、ＡＩに頼んだ分は、そのままです

品詞を色で見分ける

⑴ の解析画面には、英文を単語ごとに分けて、品詞ごとに色と下線で表示する欄があります。品詞は、名詞・代名詞・動詞・助動詞・形容詞・副詞・前置詞・接続詞／関係詞・冠詞／限定詞・その他の10種類です。凡例の品詞名を押すと、その品詞だけが目立ちます。

語ごとの品詞を、解析結果に入れる

解析のＪＳＯＮに、words という項目を足しました。英文を半角スペースで区切った語に、品詞のコードを付けたものです。

"words": [{"w":"Ms.","p":"n"}, {"w":"Tanaka,","p":"n"}, {"w":"who","p":"conj"}, {"w":"joined","p":"v"}, …]

句読点は、語に付けたままにします。語を区切るところまでＡＩに任せると、ずれやすいためです。「Tanaka,」の品詞は、カンマを除いた語そのものの品詞です。

AI の返事は、そのままでは使わず、語を半角スペースでつなぐと、原文と完全に一致するときだけ採用します。合わなければ、色分けだけを付けません。解析の他の部分は、そのまま残します。

function cleanWords(ws, text) {
  // …語ごとに p を確かめ、不明なコードは "other" にする
  return norm(out.map(x => x.w).join(" ")) === norm(text) ? out : null;
}

品詞コードの確かめには、POS[x.p] ではなく、hasOwnProperty を使っています。POS["__proto__"] が、真の値になってしまい、__proto__ という名前の品詞が、そのまま通るためです。試験の途中で見つけた欠陥でした。

色だけに頼らない

色だけで区別する表示は、色の見分けにくい人には読めません。そこで、色のほかに、下線を引き、「品詞名も表示」のチェックで、各語の下に、品詞名を出せるようにしました。ダークモード用の色も、別に用意しています。

後から足す

すでに解析した英文には、あとから品詞を足せます。

  • 1文ずつ：「品詞を付ける」を押すと、その英文だけ、品詞を判定します（区切りごとの形も、いっしょに判定します）
  • まとめて：ライブラリの「表示中の品詞・区切りの形を一括で付ける」です。ＡＰＩは1文ずつ、コピペモードは10文ずつ、プロンプトにまとめます
  • 受信箱・復元から：同じ英文が届いたとき、品詞のない英文には、品詞だけを足します（後の節）

単語に発音記号（ＩＰＡ）を付ける

⑴ の「単語・熟語」と単語帳には、単語の横に、アメリカ英語の発音記号が出ます（例：applicant → /ˈæplɪkənt/）。🔊 を押すと、実際の読み上げも聞けます。

単語に ipa という項目を足す

解析のＪＳＯＮの vocab（単語の一覧）と、単語帳の単語に、ipa という項目を足しました。単語帳に追加するときは、この項目も引き継ぎます。

"vocab": [{"word":"applicant","pos":"名詞","meaning":"応募者","ipa":"ˈæplɪkənt", ...}]

発音記号は、使える文字だけを受け付けます。/ / や [ ] は外して中身だけを持ち、英字・ＩＰＡの記号・強勢の印・空白・括弧・ハイフン以外が混じっていたら、その単語の発音記号だけを捨てます。長さは80字までです。ＡＩの返事や、外から届くデータに、<b> のような文字列が混じっても、画面には出ません。

function cleanIpa(s) {
  if (typeof s !== "string") return "";
  const t = s.trim().replace(/^[\/\[]+|[\/\]]+$/g, "").trim();
  return t.length > 0 && t.length <= 80 && /^[A-Za-z\u00C0-\u03FF\u1D00-\u1DBF\u203F.\s()\-]+$/.test(t) ? t : "";
}

新しい解析は、ＡＩが付ける

プロンプトの vocab に ipa（アメリカ英語、/ / は付けない、熟語は語ごとにスペースで区切る）を足しました。ＡＩの発音記号には誤りが混じりうるので、気になる語は、辞書で確かめる前提です。

samples は、辞書から機械的に作った

samples の単語 379 語には、ＡＩを使わず、発音辞書（CMU Pronouncing Dictionary、アメリカ英語）から機械的に作った発音記号を入れました。辞書は、音を、ＡＲＰＡＢＥＴという記号の並びで持っているので、これをＩＰＡに置き換えています。

  • 強勢の印：辞書は、強勢を母音に付けます。ＩＰＡでは、強勢の印を音節の頭に置くので、母音の前の子音のまとまりから、音節の頭になれる並び（pl、str など）を機械的に選んで、その前に置きました（kəmˈplit、ˈstɹætədʒi）
  • 熟語：語ごとに変換して、スペースでつなぎます。of・to・the などの機能語は、弱い発音（əv、tə、ðə）にしました
  • 辞書に無い語：résumé・repave・intranet の3語だけ、手で付けました。この3語は、辞書での確認をしていません

379 語すべてが、上の検査（使える文字だけ）を通りました。

後から足す

受信箱・復元・「サンプル英文を入れる」で、同じ英文や同じ単語が届いたとき、発音記号が無い単語にだけ、発音記号を足します（ほかの項目は上書きしません）。英文の単語（vocab）は、語の綴りで突き合わせます。単語帳の単語にも、同じように足します。ただし、samples のＪＳＯＮには単語帳の単語が入っていないので、単語帳に付くのは、⑴ から追加した単語だけです。

既存の単語帳の単語に、発音記号を一括で付けるボタンは、まだありません。

関係図は RelaGrid に任せる

⑶ の関係図は、同じ作者の RelaGrid の描画部分（5ファイル）を同梱して描いています。RelaGrid は、短いテキスト（DSL）から図を作る仕組みなので、英文の解析結果から DSL を組み立てれば、そのまま図になります。

  • 解析結果から作る（ＡＩ不要）：elements のＳ・Ｖ・Ｏ・Ｃを1行目に語順どおり並べ、Ｍ（修飾語）を2行目に置いて、修飾先へ点線の矢印を引きます。時制は動詞のノートにします
  • ＡＩで詳しく作る：節（主節・従属節）を枠（ゾーン）で囲んだ DSL を、Gemini に直接書かせます。返ってきた DSL は RelaGrid のパーサーに通し、エラーがあれば行番号つきで表示します

DSL は画面上で直接直せます。RelaGrid のエディタに貼れば、さらに細かく編集できます。

スマホで「描かれない」ように見えた

RelaGrid の図は、グリッドの外側にも、左右に広い余白が付きます。スマホの幅では、図が画面より横に広く、見えている範囲が、左側の空白だけになることがありました。図は描かれているのに、「描画されない」ように見えたのです。

そこで、描いたあとに、図の中身（ゾーン・矢印・ノード・文字）の外枠を測り直して、表示範囲を、その外枠に合わせて切り詰めます。

// 中身の外枠(getBBox)に、14 の余白を足して、viewBox・幅・高さ・背景を決め直す
s.setAttribute("viewBox", `${x0} ${y0} ${w} ${hh}`);

そのうえで、図を画面の幅に合わせて縮めて表示します。細部を見たいときは、「拡大して見る（横にスクロール）」で、元の大きさに切り替えられます。保存する SVG も、余白を切り詰めた形になります。

イラストは OpenMoji で描く

⑷ では、Gemini に「どの絵文字を、どこに、どの大きさで置くか」だけを JSON で答えさせ、絵はアプリ側で並べます。on / under / next to のような位置関係を、配置で見せるためです。

絵柄は、端末の絵文字ではなく OpenMoji（CC BY-SA 4.0）を使っています。端末ごとに絵柄が変わらず、学習用の図として見た目がそろうためです。OpenMoji の画像は、絵文字の文字コードをファイル名にして取得します。

// 例：☕️ は「2615」＋異体字セレクタ「FE0F」。OpenMoji のファイル名は FE0F を外した 2615.svg
for (const c of uniq([cps.filter(c => c !== "FE0F").join("-"), cps.join("-"), cps[0]])) { … }

異体字セレクタ（FE0F）の有無はファイルによって違うため、「外した名前」「そのままの名前」「先頭の1文字だけ」の順に試します。どれもなければ、端末の絵文字で代わりに描きます。

  • バージョンを固定（openmoji@17.0.0）して、jsDelivr から読み込みます。Service Worker でキャッシュするので、一度表示した絵柄はオフラインでも出ます
  • 「SVG を保存」では、画像を data: URI にして埋め込みます。保存したファイルを、ほかの場所でもそのまま開けます
  • 右下には、ライセンス表記（Emoji: OpenMoji (CC BY-SA 4.0)）を入れています

ＡＩに図形でイラストを描かせる「SVGイラスト」も選べます。ＡＩが書いた SVG は、そのままページに埋め込まず、<img> の画像として表示します。<img> で読み込んだ SVG の中のスクリプトは実行されないので、万一おかしなコードが混ざっても動きません。

音声は「画面」ではなく「機能」にした

音声は、ブラウザの読み上げ機能（speechSynthesis）だけで作っています。無料で、オフラインでも動きます。

最初は、「⑸ 音声化」という専用の画面を作りました。でも、すぐに、2つの問題が出ました。

  • 重なっていた。 英文の画面にも、「🔊 読み上げ」のボタンがあり、専用の画面と、役目が似て見えました。
  • 食い違っていた。 ボタンは、いつも「1倍」の標準の声で読みます。専用の画面は、設定した速さ・声で読みます。同じ英文なのに、聞こえ方が違いました。

そこで、専用の画面をやめて、音声をどの画面からでも使える機能に作り直しました。

役目 置き場所
1回読む 英文・単語のある場所の ▶ ボタン（ライブラリの各行・グループ・単語帳・弱点集計・英文生成・4択問題）
続けて再生する 一覧の「この一覧を続けて再生」と、画面の下の小さなプレーヤー
練習する 英文の画面の「音声練習」のカード
設定する 「設定 → 音声」の1か所

設定を1か所にする

すべての音声が、同じ関数 say() を通り、設定（声・速さ・繰り返し・間）を、同じ場所から読みます。ボタンも、プレーヤーも、練習も、同じ設定を使うので、食い違いは起きません。

プレーヤーは、1文を読み終えるたびに設定を読み直します。再生中に速さを変えても、次の1文から反映されます。

「続けて再生」は、必須ではない

「たくさんの英文を、続けて再生」が、ＴＯＥＩＣの学習に必要かどうかも、考え直しました。結論は、「必須ではない。通勤や家事のあいだに、画面を見ずに耳で浴びたいとき（音への慣れ・表現の定着）に便利」です。

ＴＯＥＩＣのリスニングは、音声が1回しか流れず、文字もありません。問題も、1文ずつの孤立した文ではなく、短い会話や説明文です。そのため、練習の中心は、続けて再生ではなく、次の3つに置きました。

  • シャドーイング：音に慣れ、速さについていく
  • 聞き取り：文字なしで聞いて、聞き取れない部分を知る
  • 速さの調整：本番に近い速さに合わせる

続けて再生は、一覧の中の便利な機能として残し、既定の「間」は、短く（0.5秒）しました。

プレーヤーが、画面を移っても続く理由

プレーヤーは、各画面の中ではなく、ページの一番下に1つだけ置いています。画面（タブ）を切り替えても、描き直されません。再生の状態（何番目か・再生中か）は、画面とは別に持っています。

ループが2つ同時に走らないよう、再生を始めるたびに世代番号を1つ進め、古いループは、自分の番号が古くなったことに気づいて、止まります。

const tk = ++au.token;                 // 新しい再生を始める
const alive = () => tk === au.token;   // 番号が変わっていたら、自分は古い再生
await say(parts[p], "en-US", rate);
if (!alive()) return;

シャドーイングの「間」

シャドーイングの「間」は、直前に読み上げにかかった時間を測って、その1.1倍（と0.3秒）だけ待つ形にしています。英文の長さに合わせて、まねする時間が、自動で伸び縮みします。

const t0 = Date.now(); await say(text, "en-US", rate);
const gap = c.gap === "shadow" ? (Date.now() - t0) * 1.1 + 300 : …;

スラッシュリーディングの区切り（解析結果の slash）ごとに読み上げることもできます。いま読んでいる区切りは、プレーヤーの中で色が付きます。

聞き取りの答え合わせ

聞き取り練習は、英文を隠して流し、聞こえたとおりに入力してもらい、語ごとに答え合わせをします。完全に同じかどうかではなく、「どの語が聞き取れなかったか」を見せるためです。

  • 大文字・小文字と、句読点は、無視します。
  • 原文と入力を、語の列として比べ、順番を保ったまま最も多く一致する語（最長共通部分列）を探します。1語抜けても、それ以降がずれて、全部が間違いにならないようにするためです。
  • 一致しなかった原文の語を、赤で示します。余計に入力した語は、採点に影響しません。
dp[i][j] = ow[i].n === T[j] ? dp[i+1][j+1] + 1 : Math.max(dp[i+1][j], dp[i][j+1]);

答え合わせをすると、その英文の復習回数が1つ増えます。聞き取りも、「復習した」と数えるためです。

間違いと復習を記録する

英文を貯めるだけでは、覚えたかどうかが分かりません。そこで、英文と単語ごとに、学習の記録を持たせました。すべて省略できる項目にして、記録がなくても今までどおり使えます。

項目 内容
status 未学習 / 学習中 / 覚えた。手動で切り替えます（自動では変えません）
level 難易度の目安（600・730・860点）。ＡＩが付け、手動でも直せる
verified 解析結果を人が確認したか
mistakes 間違いの履歴（日付・分類・メモ）
review_count / last_reviewed 復習した回数と、最後の日

間違いは分類して数える

4択問題で不正解だったとき、「品詞」「時制」「前置詞」など13の分類から選んで記録します。分類は固定のリストです（自由入力は、メモに書きます）。リストが固定だと、あとで数えられるからです。

分類の初期値は、ＡＩに頼らず推測します。4択問題の論点（type）と、解析結果の文法ポイントの文字から、いちばん先に当てはまる分類を選びます。問題を作るときのプロンプトには、論点を同じ13分類から選ばせているので、たいていはそのまま当たります。外れたときは、記録する前に直せます。

const CAT_RX = [["品詞", /品詞/], ["時制", /時制/], ["受動態", /受動/], ["関係詞", /関係/], …];
function guessCat(texts) {
  for (const t of texts) { if (CATS.includes(t)) return t; for (const [c, rx] of CAT_RX) if (rx.test(t)) return c; }
  return "その他";
}

「弱点集計」の画面は、間違いを分類ごとに数えて、多い順に棒で並べるだけです。棒を押すと、その分類で間違えた英文の一覧に移れます。期間（直近7日・30日・全期間）で絞れます。グラフのライブラリは使わず、<span> の幅で描いています。

「覚えた」を除いて、順に復習する

英文の一覧と単語帳は、既定で「覚えた」を除いて表示します。覚えたものを毎回見せないためです。ライブラリの「この条件で復習を始める」を押すと、いまの絞り込み結果（状態・難易度・グループなど）だけを、「前へ／次へ」でたどれます。

「前へ／次へ」は、もともと全英文を順にたどるものでした。それを、画面を開いたときに渡された一覧（navList）だけをたどる形にして、一覧から開いたときは、表示中の英文の並びを渡すようにしました。弱点集計から開いたときも、同じ仕組みで、その分類の英文だけをたどれます。

復習回数は、英文は4択に答えたとき、単語は隠した意味を見たときに増やします。問題を解いたり意味を確かめたりしたことが、いちばん確かな「復習した」の印だからです。

ＡＩの解析は「未確認」として保存する

ＡＩの解析には、誤りが混じることがあります。そこで、解析の直後は verified: false で保存し、一覧と画面に「未確認」の目印を出します。和訳・文型・時制・文の要素・文法ポイント・単語は、画面から直接直せます。直したら「確認済みにする」を押します。確認済みの解析を再解析するときは、上書きの確認を出します。

古いデータを「未確認」にしてしまうと、今までの学習が止まります。そこで、読み込むときに verified がないデータは、確認済みとして扱います。

古いデータを壊さない

項目を足すたびに、保存データ・バックアップ・同期の3か所で古いデータに出会います。そこで、英文と単語を読み込む入口を1つの関数にそろえ、足りない項目を既定値で補うようにしました。

function normItem(i) {
  i.level = normLevel(i.level);                          // 600・730・860 以外は null（未判定）
  if (typeof i.verified !== "boolean") i.verified = true;   // 既存データは確認済み
  if (!STATUS[i.status]) i.status = "new";
  i.mistakes = Array.isArray(i.mistakes) ? i.mistakes : [];
  …
}

単語は、もとの「覚えた」のチェック（known）を、状態の「覚えた」に読み替えます。同期で受け取るデータも、ハッシュを計算する前に補います。受け取った直後の中身と、手元の中身が同じ形になるので、「変更あり」と誤認されて余計に送り返すことがありません。

英文を自分で集めずに作る

英文は自分で集めるものでしたが、探す手間が大きいので、ＡＩに作らせる機能も付けました。テーマ・文法項目・難易度・件数を指定すると、ＴＯＥＩＣ風のビジネス場面のオリジナル英文を作ります。

  • 既存の問題を再現させない。 プロンプトに「既存の問題集・公式問題・書籍・ウェブサイトの文を再現・引用しない」と明記し、会社名や人名も架空のものにさせます。ＡＩは、学習した文をそのまま出してしまうことがあるためです。それでも、完全には防げません。市販教材の文と偶然似ることはありうるので、そのまま配布・公開はしないでください
  • 採用した英文だけを加える。 作った英文は一度、一覧に出します。採用する文だけにチェックを残して追加します。すでにある英文と同じ文は、最初から除きます
  • 解析まで続けられる。 「追加後にそのまま解析する」を選ぶと、追加した英文を、ライブラリの一括解析と同じ処理に渡します。解析した英文は「未確認」になります

難易度は、解析のプロンプトに、3段階の目安を書いて判定させています。

難易度 目安
600 基本的な語彙と単文中心
730 関係詞・分詞などで修飾が長い、ビジネス語彙を含む
860 複数の節が入れ子になる、provided that などの語法、抽象度の高い語彙

ＡＩの返事に難易度がなかったり、600・730・860以外だったりしても、解析は失敗させません。未判定（null）にするだけです。手で決めた難易度は、再解析で上書きしません。解析と生成は、コピペモードでも同じ流れで使えます。

  • 英文はオリジナルです。 公式問題集などの文は含めていません。会社名や人名は架空のものです。1セット目は、人事・会議と出張・契約と財務・広告と顧客対応・社内通知の5つの場面で、2セット目は、そこに物流・製造とＩＴ・施設の場面を加えました。どちらも、Part 5 の文法・語彙を意識して作っています。2セット目には、if を省いた倒置の仮定法、the more … the more …、so … that … のような、1セット目にない文法も入れました
  • グループも一緒に入ります。 CSV の2列目に、グループ名を「、」でつないで書きます（例：Part 5 文法、ビジネス:人事）。読み込むと、無ければグループを作って、英文を振り分けます。2つのセットは、同じグループ名を使うので、両方を読み込むと、同じグループにまとまります
  • 同じ英文は、重複して入りません。 すでにある英文に、品詞・区切りの形・問題・イラスト・関係図のうち足りないものがあれば、足します。 解析結果（手直しした訳など）、確認済みの状態、学習状態、間違いの記録は、上書きしません。2回目に押しても、何も増えません
  • オフラインでも使えます。 一度開けば、サンプルもサービスワーカーがキャッシュします

ＡＰＩなしで、全部の機能を試せるようにする

サンプルの目的は、ＡＰＩキーがなくても、アプリの機能を全部試せることです。ＡＩが作るものを、先に作って、データに入れておきました。

ＡＩが書いたものは、誤りがあっても、文章としては自然に見えます。そこで、60文と30文を6つ・3つに分けて、並行して作らせ、機械で検査してから、サンプルに書き込みました。

解析の作り方

Gemini に10文ずつコピペして解析すると、90文で9回のやり取りになります。そこで、解析済みのファイルも用意しました。形は、アプリが「バックアップ保存」で書き出すものと同じです。そのため、読み込みには「復元」をそのまま使え、専用の取り込み機能は要りません。

暗号化したクラウド同期


英文は、まず端末のブラウザ（localStorage）に保存します。ＰＣとスマホで共有したいときのために、Cloudflare の D1 に置く同期を付けました。ただし、集める英文には公開できない文書の一部も含まれうるため、サーバーには読める形で置かないことにしました。

鍵は端末の外に出ない

  • パスフレーズから鍵を作ります。 PBKDF2（SHA-256・60万回）で、AES-GCM の256ビットの鍵を作ります。60万回くり返すのは、パスフレーズの総当たりを遅くするためです
  • 英文は1件ずつ暗号化してから送ります。 英文・単語・グループを、それぞれ JSON にして、毎回ちがう乱数（IV）で AES-GCM 暗号化します
  • パスフレーズも鍵も送りません。 サーバーにあるのは、暗号文と、鍵を作るためのソルト（公開してよい値）だけです。Cloudflare の管理画面からデータベースを見ても、英文は読めません

暗号化には、ブラウザ標準の Web Crypto API を使っています。暗号の処理を自分で書いたり、外部のライブラリを読み込んだりはしていません。

2台目の端末では、同じパスフレーズから同じ鍵を作ります。パスフレーズが合っているかは、作成時に「決まった文字列を暗号化したもの」を保存しておき、それを復号できるかで確かめます。パスフレーズを忘れると、誰にも復元できません。

接続できるのは持ち主だけ

アプリは公開ページなので、誰でも開けます。同期の入口を持ち主だけに限るため、鍵とは別に、次の3つを組み合わせています。

仕組み 役割
同期キー 作成時に発行する「保管庫ID.秘密（32バイトの乱数）」。毎回の通信で送り、サーバーは秘密の SHA-256 だけを保存して照合する
セットアップコード 保管庫を作るときにだけ必要なコード（Worker のシークレット）。他人が先に作れないようにする
MAX_VAULTS = 1 作れる保管庫は1つまで。持ち主が作った後は、誰も作れない

照合には、一致するまでの時間で中身を推測されないよう、crypto.subtle.timingSafeEqual を使っています。

同期キーはQRコードで渡す

同期キーは60文字ほどあり、スマホで手入力するのは現実的ではありません。そこで、設定画面の「スマホで接続（QRコード）」で、PCの画面にQRコードを出し、スマホのカメラで読み取るだけで接続できるようにしています。

QRコードに入れるのは、アプリのURLの末尾に、同期キーを付けたリンクです。

const q = qrcode(0, "M");
q.addData(location.origin + location.pathname + "#sync=" + encodeURIComponent(sync.token));

同期キーは # より後ろ（フラグメント）に入れます。この部分は、ブラウザがサーバーに送らないので、Cloudflare のアクセス記録にも残りません。スマホでリンクを開くと、設定画面が自動で開き、同期キーが入った状態になります。そのうえで、アドレス欄からは history.replaceState で消します。あとは、パスフレーズを入力するだけで接続できます。

  • 同期キーだけでは中身を読めません。 データを読むには、別に覚えておくパスフレーズが必要です。QRコードを人に見られても、すぐにデータが読まれるわけではありません。ただし、同期キーがあれば暗号文を取得できてしまうので、人に見られない場所で表示するよう、画面に注意書きを出しています
  • QRコードの生成は、ブラウザの中で行います。 生成に使う qrcode-generator（MIT）は、外部から読み込まず、アプリに同梱しています。同期キーを外部のサービスに渡して画像を作ってもらうことは、していません
  • すでに同期している端末で開いたときは、何もしません。 「この端末はすでに同期しています」と表示するだけで、上書きはしません

送るのは、変わったものだけ

同期のたびに全件を送ると、解析結果の大きい英文が増えるほど重くなります。そこで、最後に同期した時点の各レコードのハッシュを端末に覚えておき、いまの中身のハッシュと違うものだけを送ります。手元から消えたレコードは「削除」として送ります。

const h = hashOf(o);
if (sync.hashes[kk] !== h) out.push({ kk, h, rec: { kind, id: o.id, ...await encrypt(o, key) } });

この方式だと、英文を編集する処理のあちこちに「変更した」という印を付けて回る必要がありません。保存のたびに、3秒待ってから同期を始めます（続けて編集しているあいだは待ち直します）。

受け取る側は、サーバーが付ける通し番号（seq）で管理します。送信のたびに保管庫の番号を1つ進め、その回のレコードに同じ番号を付けます。端末は「どの番号まで受け取ったか」（since）を覚えておき、それより後のものだけをもらいます。

  • 自分が送ったときは、since を進めません。 自分の送信と同時に別の端末が送っていると、その分を飛ばしてしまうためです。自分の送ったものは次の受信で戻ってきますが、ハッシュが同じなので何も変わりません
  • 両方で同じレコードを変えていたら、この端末の変更を優先します。 受け取った側を捨てて、次の送信で上書きします。1人で使う前提なので、単純さを優先しました
  • 同じ英文が両方にあれば、1つにまとめます。 2台目を初めてつなぐと、同じ英文が別々のIDで登録されていることがあります。まだ同期していない手元の英文が同じ文なら、グループや解析結果を受け取った側に移して、手元の分を消します

Service Worker は、/api/ へのアクセスをキャッシュしません。古い応答を返すと、同期がずれるためです。

受信箱：パスフレーズを渡さずに、英文を預ける

ここまでの同期は、パスフレーズを知る端末だけが英文を書き込めます。それで困ったのが、Claude Code に英文を入れてもらいたいときです。パスフレーズを AI に渡してしまうと、鍵をかけた意味がなくなります。

そこで、「読めないけれど、預けることはできる」入口を、別に作りました。郵便受けのようなものです。

誰が 持っているもの できること
預ける側（Claude Code） 公開鍵・書き込み専用の合言葉 英文を暗号化して預ける。預けたあとの英文は、自分でも読めない
サーバー 暗号文・合言葉のハッシュ・暗号化した秘密鍵 預かる。中身は読めない
あなたの端末 パスフレーズから作った鍵 秘密鍵を開き、預けられた英文を復号して登録する

公開鍵で暗号化する

預ける側が知っているのは、公開鍵だけです。公開鍵で暗号化したものは、対になる秘密鍵でしか開けません。ただし、公開鍵暗号は大きなデータを扱えません。そこで、1通ごとに使い捨ての AES 鍵を作って本文を暗号化し、その AES 鍵を公開鍵で包んで一緒に送ります（ハイブリッド方式）。

const data = await subtle.encrypt({ name: "AES-GCM", iv }, aes, new TextEncoder().encode(JSON.stringify(payload)));
const wrapped = await subtle.encrypt({ name: "RSA-OAEP" }, pubKey, await subtle.exportKey("raw", aes));

秘密鍵は、保管庫の鍵（パスフレーズから作る鍵）で暗号化して、サーバーに置きます。だから、新しい端末は、パスフレーズを入れるだけで秘密鍵を開けます。 端末ごとに鍵を配って回る必要がありません。サーバーにあるのは暗号化された秘密鍵だけなので、サーバーの管理者でも開けません。

鍵の組は、保管庫を作るときに、端末の中で作ります。受信箱ができる前に作った保管庫には、「受信箱を有効にする」で、あとから足せます。

公開鍵は、サーバーから取らない

預けるスクリプトは、公開鍵を設定ファイルから読みます。毎回サーバーから取る作りにしなかったのは、サーバー（や通信路）が公開鍵をすり替えられるからです。すり替えた側は、自分の秘密鍵で開ける暗号文を、こちらに作らせられます。公開鍵を最初から手元に持っておけば、サーバーが乗っ取られても、預けた英文は読まれません。

書き込み専用の合言葉

預けるには、同期キーとは別の書き込み専用の合言葉を使います。サーバーには SHA-256 のハッシュしか保存しません。

  • この合言葉では、同期データも、受信箱の中身も読めません（どちらも 401 になります）。漏れても、できるのは「預ける」ことだけです
  • アプリから、いつでも無効にでき、再発行もできます。再発行すると、古い合言葉は使えなくなります
  • 荒らされないよう、上限を置きました。1通は 1.5MB まで、たまるのは 200 通・合計 20MB までです。いっぱいのときは、「アプリを開いて同期し、受け取ってから送り直してください」と返します

受け取るのは、あなたの端末

預けられた英文は、アプリが同期するたびに受け取ります。1通ずつ、秘密鍵で AES 鍵を開き、本文を復号して取り込みます。取り込み終わったら、サーバーから消します。

  • 保存してから消す。 端末に保存したあとで受信箱から消すので、途中で止まっても失われません。もう一度受け取っても、同じ英文は重複として除かれ、二重にはなりません
  • 壊れた通は捨てる。 復号できない・形が違う通は、取り込まずに捨てます。1通でも詰まると、あとの通が受け取れなくなるためです

外から来たデータは信用しない

合言葉さえあれば、誰でも預けられます。合言葉が漏れた場合も考えて、取り込むときは使う項目だけを取り出します（英文は500字まで、解析は大きさの上限つき）。状態・復習回数・間違い・ブックマークのような、学習の記録は受け取りません。解析がついた英文は「未確認」にします。品詞・区切りの形・4択問題・イラスト・関係図も受け取りますが、それぞれの形を確かめて、通ったものだけです。

function cleanItem(i) {
  const an = i.analysis && typeof i.analysis === "object" && JSON.stringify(i.analysis).length < 30000 ? i.analysis : null;
  const o = { text: clip(i.text, 500), bm: false, added: Date.now(), analysis: an, level: i.level, verified: an ? false : true };
  const q = cleanQuiz(i.quiz), il = cleanIllus(i.illus), rl = cleanRel(i.rel);
  if (q) o.quiz = q; if (il) o.illus = il; if (rl) o.rel = rl;
  return o;
}
項目 受け取る条件
4択問題 選択肢が4つで、互いに異なる。正解の番号が0〜3。空所（______）がある
イラスト 絵文字の場面だけ。外から届く SVG は受け取りません。色は決まった形のものだけ。位置と大きさは範囲内に丸める
関係図 RelaGrid のパーサーが、エラーなく読めるもの。4,000字まで
品詞 語をつなぐと、原文と一致するもの。不明なコードは「その他」
区切りの形 区切りをつなぐと、原文と一致するもの。2〜12個で、形が空でないもの

画面に出すときは、もともと文字として表示（エスケープ）しています。実際に、<script> を含む英文、巨大な解析、__proto__ という名前のグループを預けて試しましたが、使う項目だけが取り込まれ、画面への影響はありませんでした。

すでにある英文には、足りないものだけを足す

同じ英文が届いたとき、いままでは、重複として捨てていました。いまは、手元の英文に足りないもの（品詞・区切りの形・問題・イラスト・関係図）があれば、それだけを足します。

function fillMissing(ex, i) {
  const q = cleanQuiz(i.quiz); if (!ex.quiz && q) { ex.quiz = q; c = true }
  // 品詞・区切りの形・イラスト・関係図も同じ。ex.analysis（解析）や status などには触れない
}

あとから問題やイラストを作って、すでに使っている英文に、学習の記録を壊さずに足すための仕組みです。何度届いても、足りないものがなくなれば、何も起きません。

node tools/inbox-send.mjs public/samples/toeic-sentences.csv --dry-run   # 件数だけ確かめる

限界と使うときの注意

  • パスフレーズを忘れると、クラウドのデータは復元できません。 端末に残っているデータは使えます
  • ＡＩに送った英文は、Google 側に渡ります。 Gemini API の無料枠や Gemini アプリの設定によっては、学習に使われる場合があります。公開できない英文は、ＡＩにかけないか、設定を確認してから使ってください
  • 「バックアップ保存」で書き出す JSON ファイルは、暗号化されません
  • 端末側の保存先（localStorage）は、ブラウザごとに約 5MB までです。解析済みの英文で1,000文前後が目安です
  • 同期は「最後に書いた端末が勝つ」方式です。2台で同時に同じ英文を編集すると、片方の変更が消えることがあります
  • 読み上げの声は、端末にある音声に依存します。iPhone は、マナーモードだと音が出ないことがあります
  • 続けて再生は、スマホの画面をロックしたり、アプリを別のものに切り替えたりすると、止まることがあります（端末とブラウザによります）。画面を点けたまま使うのが確実です
  • 受信箱に預ける側（Claude Code）は、英文の中身を見ます。 送るファイルを読む必要があるためです。見られたくない英文は、受信箱に頼らず、自分で CSV から読み込んでください
  • 受信箱を使うには、保管庫が必要です。預けられた英文は、アプリが同期するときに受け取ります。アプリを開かないあいだは、暗号文のままサーバーに残ります
  • 「未確認」の目印は、人が確かめる合図であって、ＡＩの答えが正しいことの保証ではありません。直さずに「確認済み」にすれば、誤りもそのまま残ります
